## C. Целевая точка истины

| Подсистема | Канонический программный источник |
| --- | --- |
| Конфигурация | `src/config.py` |
| Движок и состояние | `src/core/engine.py` |
| Веб-API | `src/server/app.py` |
| AI-подключение | `src/ai/connector.py` |
| Загрузка и выбор документов | `src/ai/knowledge_base.py` |
| Бой | `src/systems/combat.py` |
| Квестовые цепочки/трекер/процедурная генерация | `src/systems/quests.py`, `src/systems/game_systems.py`, `src/world/procedural.py` — **разные роли, требуют будущего поведенческого аудита** |
| NPC/компаньоны | `src/world/npc_registry.py`, `src/systems/subsystems.py`, `src/systems/companions.py` — **регистр, состояние и каталог, не обязательно функциональные дубли** |
| Мир | `src/world/simulation.py`, `src/world/procedural.py` |
| Контент | `src/content/creation_data.py`, `base.py`, используемые версии `v2_legacy`–`v5_legacy` |
| Игровые JSON | `game_data/active/**` |
| Чат и ЛОР-документация | `docs/worldbuilding/**`, **не утверждённая реализация** |

Точное совпадение названий или тем в файлах ещё не является доказательством дублирующей функции. Например, `WorldSimulator.tick()` и `WorldTicker.tick()` вызываются в одном игровом шаге, но могут иметь разную ответственность; объединение без тестов может удалить поведение. При желании пользователя **убрать дубли** такие случаи надо проверять тестами ввода-вывода и владением состоянием, а не массовым удалением кода.

## D. Ограничения аудита и оставшийся технический долг

Нельзя объявлять проект полностью исправленным только после переноса файлов:

1. **Крупные монолитные модули:** `src/core/engine.py` ~1,8 тыс. строк; `src/server/app.py` ~1,35 тыс. строк; UI `static/js/app.js` ~126 КБ. Декомпозиция требует контрактных тестов; механики при этом не должны менять поведение.
2. **Legacy-слои `src/content/v2_legacy.py` – `v5_legacy.py` используются через импорты.** Их слияние нельзя выполнять просто по похожим названиям: разные данные и методы могут дополнять друг друга.
3. **JSON-контент семантически пересекается.** KnowledgeBase по имени/версии выбирает один файл внутри группы, но документы с разными названиями могут содержать противоречащие правила. ЛОР и механики нельзя слить без утверждённого канона и оценки потребителей.
4. **Глобальный объект `engine` на Flask-процесс** — потенциальное смешение состояний при одновременной работе нескольких независимых игроков. Пока считать архитектуру одной локальной игровой сессии, не готовой многопользовательской.
5. **Ошибки данных:** основной KB при ошибочном JSON увеличивает счётчик и продолжает работу; для пользовательской БД отдельный механизм. Требуется схема, диагностика и явные ошибки для критических данных.
6. **Сохранения:** новые имена защищены от обхода пути, но сериализация и обратная совместимость старых сейвов не были исчерпывающе проверены на реальных пользовательских файлах. Сделать резервную копию `saves/` до обновления.
7. **Безопасность:** устранены конкретные дефекты, **не было полноценного пентеста**. Не выставлять Flask API публично.
8. **CI не проверяет настоящую AI-инференцию**, облачные API, GUI лаунчера, PyInstaller Windows-сборку, большую нагрузку и все сценарии состояний. Отсутствие падений smoke-тестов не доказывает полную готовность игры.
9. **ЛОР против старых игровых JSON:** `game_data/active/world/lore_chronology.json` и другие исторические документы ещё требуют сверки с новым согласованным каноном. Не менять сюжет без утверждения пользователя.

## E. Проверка после очистки

- `python scripts/validate_install.py` — структура, уникальность имён активных JSON, валидность синтаксиса Python и JSON.
- `python -m pytest -q` — имеющиеся тесты плюс регрессии загрузки данных, пути сохранений, наличия модулей и health endpoint.
- GitHub Actions запускает те же проверки на PR и push в main.
- `python -m src.server.app` → `http://127.0.0.1:8080/health`, возвращает JSON `{"status":"ok"}`.
- Успех автоматических тестов описывает только проверенное поведение; неподтверждённые интеграции остаются в перечне долга.

## F. Согласованный порядок дальнейшей работы

1. **Техническая стабилизация** — завершить PR, устранить падения CI, подтвердить запуск, не вводить новые механики.
2. **ЛОР** — вернуться к магии, природе воздействия, академиям, государствам, кланам, истории и экономике; вести канон в `docs/worldbuilding`.
3. **После завершения и утверждения ЛОРа** — согласовать игровые контракты, механики, события, квестовые хуки и интеграционные тесты.
4. Не смешивать массовое перемещение/очистку с редизайном механик в одном PR.
